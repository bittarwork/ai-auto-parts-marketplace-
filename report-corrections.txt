3. CHAPTER 1 - INTRODUCTION
======================================================================

PASTE THIS INSTEAD OF THE CURRENT INTRODUCTION SECTION:

Chinese vehicle brands such as Chery, Geely, MG, Great Wall, Haval, and Changan have gained a strong presence in the Saudi Arabian automotive market over the past decade. Their affordability, availability, and expanding model range have increased the demand for genuine and compatible spare parts across the Kingdom. As a result, customers increasingly rely on online channels to search for and purchase vehicle parts for maintenance and repair.

Despite this growth, existing online platforms still present significant limitations. Customers often struggle to identify the correct parts for their vehicles, confirm compatibility, compare available options, and obtain reliable guidance before purchase. These limitations frequently lead to ordering mistakes, delays, and additional cost. Suppliers and platform operators also face challenges related to product organization, customer support, and efficient management of catalog and order data.

To address these issues, this project developed RedParts, an AI-supported e-commerce platform specialized in Chinese auto parts for the Saudi market. The system integrates AI-assisted search, a context-aware chatbot, compatibility verification, personalized recommendations, structured product browsing, and an administrative dashboard. The aim of the project is to demonstrate how modern web technologies and practical AI integration can improve customer trust, reduce part-selection errors, and support more efficient digital commerce in a specialized automotive domain.

The rapid growth of Chinese vehicle ownership in Saudi Arabia has created increasing demand for reliable online access to genuine and compatible spare parts. However, customers still face major challenges when searching for and purchasing these parts online. Existing platforms often rely on basic category browsing and keyword search, provide limited compatibility support, and offer little personalized guidance during the purchase process.

These limitations create several practical problems:

1. Difficulty identifying the correct part for a specific vehicle
2. Limited support for verifying vehicle-part compatibility before purchase
3. Weak search tools that do not interpret natural-language automotive queries effectively
4. Lack of personalized recommendations based on vehicle or purchase context
5. Dependence on manual customer support for many product-selection questions
6. Limited analytical visibility for administrators managing products, users, and orders

As a result, customers may place incorrect orders, lose confidence in online purchasing, or require additional support before completing a transaction. This project addresses these problems through an AI-supported e-commerce platform designed specifically for this automotive domain.

14. CHAPTER 4 - FRONTEND ARCHITECTURE

The frontend application is organized using a feature-based structure that separates pages, reusable components, contexts, service modules, and utility helpers. This organization supports maintainability and allows domain-specific functionality to remain modular across both customer-facing and administrative parts of the interface.

The pages directory contains route-level components for the storefront and the administrative dashboard. Administrative pages are grouped under a dedicated namespace and rendered through a separate layout component that provides isolated navigation and role-restricted access. Reusable interface elements are organized into functional component groups such as layout components, product components, search components, chatbot components, common UI elements, and administrative UI components. This separation improves reuse and consistency across the application.

Global application state in the implemented interface is managed primarily through React Context providers, particularly for cart behavior, wishlist behavior, and theme selection. API communication is handled through Axios-based service modules that centralize requests to authentication, products, orders, categories, vehicles, wishlist operations, administrative endpoints, and AI-assisted features.

The current implementation operates in English and LTR layout. An initial internationalization structure is present in the frontend codebase, but full Arabic translation coverage and RTL interface behavior remain incomplete and are treated as future enhancement work.

15. CHAPTER 4 - BACKEND ARCHITECTURE
======================================================================

PASTE THIS INSTEAD OF THE CURRENT BACKEND ARCHITECTURE SECTION:

The backend is implemented as a Node.js and Express.js REST API following a layered controller-service-model structure. This architecture separates HTTP request handling, business logic, AI-related processing, and database access responsibilities into distinct modules, improving readability and maintainability.

Incoming requests pass through a global middleware pipeline that includes Helmet for security headers, CORS handling, Morgan for request logging, compression support, and rate limiting. Additional route-level middleware is applied where required for authentication, authorization, validation, and file-upload handling.

The protect middleware verifies JWT-based authentication and attaches the authenticated user to the request context. Role checks are then enforced through authorization middleware on restricted routes. Input validation middleware is applied to key write operations and protected endpoints to improve request safety and data consistency.

Business logic is delegated to controllers and service modules. This is especially important for AI-assisted functionality, where search processing, chatbot behavior, compatibility logic, and recommendation logic are kept outside direct route definitions. The backend therefore acts as the integration layer between MongoDB persistence, Redis caching, and OpenAI-powered processing.

16. CHAPTER 4 - DATABASE SCHEMA DESIGN
======================================================================

PASTE THIS INSTEAD OF THE CURRENT DATABASE SCHEMA DESIGN SECTION:

The implemented backend defines eleven primary Mongoose models corresponding to the core platform data structures. These models cover users, products, categories, vehicles, carts, guest carts, wishlists, orders, chatbot sessions, settings, and product notifications.

The MongoDB schema design favors a document-oriented approach in which data that is frequently accessed together is often embedded within parent documents. Product records include compatibility information, image metadata, and structured product attributes. Order documents contain embedded order-item snapshots to preserve purchased product information at the time of order creation. Chat sessions store message history inside the session document to simplify retrieval of conversational context.

This schema design supports the platform's main functional requirements while remaining flexible enough for future extension. It also aligns with the domain-specific needs of automotive product data, where product attributes and compatibility details vary across categories and models.

17. CHAPTER 4 - NATURAL LANGUAGE PROCESSING SEARCH SYSTEM
======================================================================

PASTE THIS INSTEAD OF THE CURRENT NLP SEARCH SECTION:

The RedParts search pipeline enables users to search for products using natural-language automotive queries rather than relying only on exact keyword matching. The implemented search flow begins at the frontend search interface, where user queries are submitted to the backend AI search endpoint. The backend then processes the query using GPT-assisted entity extraction to identify relevant product attributes such as part type, vehicle brand, vehicle model, and model year.

The extracted information is normalized and converted into structured MongoDB query logic. When OpenAI-based processing is unavailable or insufficient, the system falls back to a keyword-based extraction approach in order to preserve search continuity. Search results may then be filtered, ranked, and enriched with compatibility-related information where user vehicle data is available.

Redis caching is used to store repeated search-processing results and reduce repeated external processing overhead. The implemented search pipeline therefore combines GPT-assisted entity extraction, application-level normalization, query construction, fallback keyword handling, and caching within a single domain-specific search workflow.

18. CHAPTER 4 - INTELLIGENT CHATBOT SYSTEM
======================================================================

PASTE THIS INSTEAD OF THE CURRENT CHATBOT SECTION:

The RedParts chatbot provides conversational customer guidance through an OpenAI-powered interaction pipeline integrated into the web application. When a user sends a message, the system retrieves or creates a persistent chat session, builds the conversational context, and submits the resulting message sequence to the OpenAI service for response generation.

The chatbot context may include recent conversation history, the user's registered vehicles, and information about the product currently being viewed. This allows the chatbot to respond in a more relevant and context-aware manner, especially for compatibility-related questions and product guidance.

Chat sessions are stored in the ChatSession collection, where message history is preserved as embedded session content. The chatbot also supports product-aware replies by attaching referenced product information where possible. Although the chatbot can advise users to seek human assistance when needed, a formal escalation workflow is not implemented as a separate system module in the current version of the platform.

19. CHAPTER 4 - PRODUCT RECOMMENDATION ENGINE
======================================================================

PASTE THIS INSTEAD OF THE CURRENT PRODUCT RECOMMENDATION ENGINE SECTION:

The recommendation engine in RedParts generates personalized product suggestions using application-level recommendation logic rather than direct generative inference. The implemented service combines multiple signals, including registered vehicle data, previous order history, compatibility metadata, category relationships, and product popularity, in order to produce recommendation sets that are relevant to the user's automotive context.

Three recommendation scenarios are supported in the implemented platform. First, similar-product recommendations are generated for product-detail pages using category and compatibility overlap. Second, complementary suggestions such as frequently-bought-together items are derived using domain-oriented matching logic and product relationships. Third, personalized recommendations can be produced for authenticated users based on registered vehicles and prior purchases.

All recommendation outputs are filtered against the live product catalog to ensure that only active and in-stock items are returned. Redis caching is used to reduce repeated recommendation processing for the same user or context. The recommendation layer is therefore implemented as a practical scoring and filtering service built on domain logic and database signals.

22. CHAPTER 4 - AUTHENTICATION AND SECURITY IMPLEMENTATION
======================================================================

PASTE THIS INSTEAD OF THE CURRENT AUTHENTICATION AND SECURITY SECTION:

Authentication in RedParts is implemented using JSON Web Tokens. After successful login, the backend issues a signed token containing the user's identifier and role information. The frontend then attaches this token to protected API requests through the Authorization header. On the backend, authentication middleware validates the token, checks its expiry, retrieves the corresponding user record, and attaches the authenticated user to the request object.

The system defines three user roles in the data model: customer, supplier, and administrator. In the current implementation, the customer and administrator workflows are the most fully realized, while supplier-oriented management remains more limited.

Security-related measures in the implemented backend include password hashing with bcryptjs, HTTP security headers through Helmet, request rate limiting, request validation for key write operations, and CORS restrictions to control accepted frontend origins. Together, these measures provide a practical security foundation suitable for the current project scope.
