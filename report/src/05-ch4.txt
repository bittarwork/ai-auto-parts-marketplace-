# التصميم

## مقدمة الفصل

يعرض هذا الفصل التصميم المعماري والتفصيلي لنظام EV Auto Parts استناداً إلى المتطلبات المحلّلة في الفصل الثالث. يبدأ بالمعمارية العامة وتوزيع المكوّنات، ثم تصميم قاعدة البيانات ومخطط الصفوف، ثم التصميم السلوكي عبر مخططات التسلسل والحالة للعمليات الجوهرية، ثم تصميم واجهة البرمجة، وينتهي بتصميم الواجهة الأمامية وبنية الشيفرة.

## المعمارية العامة

### النمط المعماري

اعتُمدت معمارية ثلاثية الطبقات (Three-tier) من نمط العميل–الخادم، مع فصل صريح داخل الخادم إلى طبقات فرعية: المسارات (Routes)، والوسطاء (Middleware)، والمتحكّمات (Controllers)، والخدمات (Services)، والنماذج (Models). ويُتيح هذا الفصل اختبار كل طبقة على حدة وتبديل التنفيذ الداخلي دون التأثير في الواجهة الخارجية؛ فمثلاً تستطيع خدمة الاستخراج اللغوي التحوّل من OpenAI إلى مزوّد آخر دون تغيير في المتحكّمات.

يوضّح الشكل 6 المكوّنات الرئيسية للنظام وتبعياتها.

### مبادئ التصميم المتّبعة

- **الخادم مصدر الحقيقة (Server-side Truth):** كل حسابات الأسعار والضرائب والشحن والمخزون تُجرى على الخادم؛ الواجهة تعرض فقط.
- **انعدام الحالة:** لا تُخزَّن حالة جلسة على الخادم؛ الهوية تُنقل عبر JWT، وهوية الزائر عبر معرّف جلسة في ترويسة `X-Cart-Session`.
- **التدهور الرشيق:** كل اعتماد خارجي (OpenAI، Redis) له مسار بديل لا يوقف الخدمة.
- **الحذف الناعم (Soft Delete):** المنتجات والفئات والمركبات تُعطَّل بعلم `isActive` بدلاً من حذفها فعلياً، حفاظاً على سلامة الطلبات التاريخية.
- **لقطات البيانات (Snapshots):** يحتفظ الطلب بنسخة من اسم المنتج ورقمه وصوره وسعره وقت الشراء، فلا تتأثر الطلبات القديمة بتعديل المنتج لاحقاً.
- **استجابة موحّدة:** كل الاستجابات بصيغة `{ success, message, data }` مع رموز HTTP دلالية.

## تصميم قاعدة البيانات

### اختيار النموذج الوثائقي

صُمّمت قاعدة البيانات على MongoDB بإحدى عشرة مجموعة (Collection) تُعرَّف بمخططات Mongoose. ورُوعي في التصميم تضمين (Embedding) البيانات التي تُقرأ دائماً مع مستندها الأب (مصفوفة التوافق والمواصفات داخل المنتج، والعناوين داخل المستخدم، وعناصر السلة داخل السلة، والرسائل داخل جلسة المحادثة)، والإشارة (Referencing) بمعرّفات ObjectId إلى الكيانات المستقلة (المستخدم، المنتج، الفئة). يلخّص الجدول 8 المجموعات وحقولها الرئيسية والفهارس.

## التصميم السلوكي

### تسلسل البحث الذكي

يعرض الشكل 8 تسلسل الرسائل بين المكوّنات عند تنفيذ بحث ذكي لمستخدم مسجّل.

FIGURE: مخطط التسلسل لعملية البحث الذكي باللغة الطبيعية
```plantuml
@startuml
actor User
participant "IntelligentSearchBar\n(React)" as UI
participant "aiRoutes\n/api/ai/search" as R
participant "aiSearchController" as C
participant "nlpProcessorService" as NLP
participant "OpenAI API" as OAI
participant "aiSearchService" as S
participant "compatibilityService" as CS
participant "searchRankingService" as RK
database "MongoDB" as DB
User -> UI : type query, submit
UI -> R : POST {query, limit}\n(optional JWT)
R -> C : optionalAuth -> intelligentSearch()
C -> NLP : processQuery(query)
NLP -> OAI : chat.completions (JSON, low temperature)
alt success
  OAI --> NLP : {partType, brand, model, year, keywords}
else failure / invalid key / timeout
  NLP -> NLP : fallbackKeywordExtraction()\nconfidence = 30
end
NLP --> C : normalized criteria + confidence
C -> S : search(criteria, user)
loop strategies: strict, no_year, no_model, no_brand
  S -> DB : find({$text, isActive, filters})
  DB --> S : products
  break products.length > 0
  end
end
opt user authenticated
  S -> DB : Vehicle.find({user, isActive})
  S -> CS : annotate compatibilityStatus per product
end
S -> RK : rankSearchResults(products, criteria, vehicles)
RK --> S : sorted products + scoreBreakdown
S --> C : results, strategy, analysis
C --> UI : 200 {success, data}
UI --> User : render results + AI analysis banner
@enduml
```

يُبرز الشكل 8 نقطة التفرّع الوحيدة الاحتمالية (استدعاء OpenAI) وكيف يُستوعب فشلها داخل الخدمة، كما يُظهر أن التحقق من التوافق يُدمج في نتائج البحث للمستخدم المسجّل قبل مرحلة الترتيب، مما يمنح المنتجات المتوافقة أعلى وزن.

### تسلسل إتمام الطلب

يوضّح الشكل 9 تسلسل إنشاء الطلب من السلة.

FIGURE: مخطط التسلسل لإتمام الطلب وإنشاء الطلبية
```plantuml
@startuml
actor Customer
participant "CheckoutPage\n(React)" as UI
participant "cartRoutes" as CR
participant "orderRoutes" as OR
participant "orderController" as OC
participant "pricing util\n(getPricingSettings,\ncalculateTotals)" as P
database "MongoDB" as DB
Customer -> UI : open checkout
UI -> CR : POST /api/cart/validate (JWT)
CR -> DB : load Cart + Products
CR --> UI : {isValid, issues[], totals}
Customer -> UI : choose address & payment, confirm
UI -> OR : POST /api/orders\n{shippingAddress, paymentMethod, notes}
OR -> OC : protect -> validate -> createOrder()
OC -> DB : Cart.findOne({user}).populate(items.product)
loop each cart item
  OC -> OC : check isActive and stock >= quantity
  OC -> OC : build orderItem with productSnapshot
end
OC -> P : getPricingSettings() -> Settings
OC -> P : calculateTotals(subtotal)\n(tax 19%, shipping 12 EUR, free >= 150 EUR)
OC -> DB : Order.create({status: pending,\npaymentStatus: pending, statusHistory[0]})
DB --> OC : order (orderNumber generated pre-validate)
OC -> DB : Product.findByIdAndUpdate($inc stock -qty, purchaseCount +qty)
OC -> DB : cart.items = []; cart.save()
OC --> UI : 201 {order}
UI --> Customer : navigate to /orders/:id
@enduml
```

يُبيّن الشكل 9 أن التحقق يُجرى مرتَين (قبل العرض وعند الإنشاء) حمايةً من تغيّر المخزون بين الخطوتَين، وأن خصم المخزون وتفريغ السلة يتمّان بعد إنشاء الطلب مباشرة. ويُلاحَظ من ناحية التصميم أن هذه العمليات الثلاث (إنشاء الطلب، خصم المخزون، تفريغ السلة) لا تُنفَّذ ضمن معاملة (Transaction) واحدة، وهو قيد يُناقَش في الفصل السابع.

### مخطط حالة الطلب

يمرّ الطلب بحالات معرَّفة في تعداد `status`. ويعرض الشكل 10 الانتقالات المقصودة في التصميم.

FIGURE: مخطط الحالة لدورة حياة الطلب
```plantuml
@startuml
[*] --> pending : createOrder()
pending --> confirmed : admin updates status
pending --> cancelled : customer cancelOrder()\nor admin
confirmed --> processing : admin
confirmed --> cancelled : customer cancelOrder()\nor admin
processing --> shipped : admin
processing --> cancelled : customer cancelOrder()\nor admin
shipped --> delivered : admin
delivered --> [*]
cancelled --> [*]
note right of cancelled
  Stock is restored for each item
  when the order becomes cancelled.
end note
note bottom of pending
  Payment status is tracked separately:
  pending | paid | failed | refunded
end note
@enduml
```

يعكس الشكل 10 الانتقالات المنطقية المقصودة؛ إلا أن التنفيذ الحالي لمسار تحديث الحالة الإداري لا يفرض هذه الانتقالات، فيقبل مثلاً الانتقال من `cancelled` إلى `confirmed`، كما أثبت الاختبار الموثّق في الفصل السادس. أما إلغاء العميل فيُرفض فقط إذا كان الطلب في حالة `shipped` أو `delivered` أو `cancelled`.

### تسلسل المحادثة مع المساعد الذكي

يوضّح الشكل 11 تدفّق رسالة محادثة من المستخدم إلى المساعد.

FIGURE: مخطط التسلسل لمعالجة رسالة في مساعد المحادثة
```plantuml
@startuml
actor User
participant "ChatWidget\n(React)" as UI
participant "/api/ai/chatbot" as R
participant "chatbotService" as CB
database "Redis\n(optional)" as RD
database "MongoDB" as DB
participant "OpenAI API" as OAI
User -> UI : send message
UI -> R : POST {message, sessionId, context.productId}
R -> CB : optionalAuth -> processMessage()
CB -> RD : get history (if available)
alt cache miss / Redis disabled
  CB -> DB : ChatSession.findOne({sessionId})
end
opt user authenticated
  CB -> DB : Vehicle.find({user}) -> vehicles context
end
opt context.productId
  CB -> DB : Product.findById -> current product context
end
CB -> CB : build system prompt\n(store info, vehicles, product, last 5 messages)
CB -> OAI : chat.completions (temperature 0.7)
alt success
  OAI --> CB : assistant reply
  CB -> DB : findMentionedProducts(reply, message)
  CB -> DB : ChatSession upsert (user + assistant messages)
  CB -> RD : cache history
  CB --> UI : 200 {message, suggestedProducts, sessionId}
else failure
  CB -> CB : getFallbackResponse(message)\n(rule-based: price / shipping / compatibility / generic)
  CB --> UI : 200 {message, error: true, fallback}\n(session not persisted)
end
UI --> User : render reply + product cards
@enduml
```

يُظهر الشكل 11 أن سياق المحادثة يُبنى من ثلاثة مصادر (مركبات المستخدم، المنتج الحالي، آخر خمس رسائل) قبل استدعاء النموذج، وأن الردّ البديل عند الفشل قائم على كلمات مفتاحية بسيطة ولا يُحفَظ في جلسة، وهو ما لاحظه الاختبار في الفصل السادس.

## تصميم الواجهة الأمامية

### مبادئ التصميم

صُمّمت الواجهة بلغة إنجليزية واتجاه من اليسار إلى اليمين، مع مراعاة مبادئ الاستخدامية المتعارف عليها [19]: إظهار حالة النظام (هياكل تحميل، إشعارات فورية، مؤشّر "Checking compatibility…")، والاتساق (مكوّنات مشتركة للأزرار والبطاقات)، والوقاية من الأخطاء (تعطيل زر الإرسال عند فراغ الحقل، التحقق من الكميات مقابل المخزون)، ومرونة الاستخدام (الوضع الليلي، البحث بالطبيعي أو بالتصفّح).

### بنية الصفحات

تنقسم الواجهة إلى تخطيطَين مستقلَّين:

- **تخطيط العميل (`Layout`):** ترويسة بروابط التنقّل وأيقونات السمة وقائمة الأمنيات والسلة والحساب، ومحتوى الصفحة، وتذييل بروابط المعلومات، وأداة المحادثة العائمة في كل الصفحات. ويضمّ 27 مساراً (بما فيها صفحة 404) منها 7 محمية بمكوّن `ProtectedRoute` (إتمام الطلب، قائمة الأمنيات، لوحة المستخدم، الملف الشخصي، الطلبات، تفاصيل الطلب، المركبات).
- **تخطيط الإدارة (`AdminLayout`):** شريط جانبي مقسّم (Main، People، Insights، System)، وترويسة بمسار تنقّل تفصيلي وبحث، ومحتوى، دون ترويسة العميل أو أداة المحادثة. ويُحمى بمكوّن `AdminRoute` الذي يتحقق من دور المدير، ويضمّ 13 مساراً فرعياً.

### إدارة الحالة والاتصال

تُدار الحالة المشتركة بثلاثة سياقات React: `CartContext` (عدد العناصر والإجماليات ومعرّف جلسة الزائر)، و`WishlistContext`، و`ThemeContext` (الوضع الليلي المحفوظ في التخزين المحلي). وتمرّ كل الاتصالات عبر نسخة Axios مركزية في `services/api.js` تُضيف رمز JWT آلياً وتُعالج استجابات 401 بمسح بيانات الجلسة المحلية، بينما تُضيف `cartService` ترويسة `X-Cart-Session` بمعرّف الجلسة المحفوظ في التخزين المحلي تحت المفتاح `cart_session_id`. ويُغلّف كل مورد بخدمة مستقلة (`productService`، `cartService`، `aiSearchService`، …).

## خلاصة الفصل

قدّم هذا الفصل تصميم النظام على مستويات ثلاثة: المعمارية العامة ثلاثية الطبقات مع مبادئ التصميم الحاكمة، وتصميم قاعدة البيانات بإحدى عشرة مجموعة ومخطط صفوف يُبرز محورية المنتج وتضمين التوافق داخله، والتصميم السلوكي عبر ثلاثة مخططات تسلسل ومخطط حالة توضّح كيف تُحصر الاحتمالية في استدعاء النموذج اللغوي وحده. كما وثّق واجهة البرمجة ومستويات الوصول وأوزان الترتيب وتصميم الواجهة الأمامية وبنية الشيفرة. ويُترجم الفصل الخامس هذا التصميم إلى تفاصيل التحقيق البرمجي.
